# アカウント連携をリゾルバ方式のエイリアスとして実装する

同一人物が持つ複数のメールアドレスから1つのカレンダーを読み書きできる「アカウント連携」機能を追加するにあたり、以下を決定した。

## 決定

- **エイリアス(統合)として扱う**: 連携は「別々のカレンダーを切り替えて見る」機能ではなく、複数のメールアドレスを1つのカレンダーの別名にする機能である。連携中はどのメールでログインしても、切り替えUIなしに同じ1つのカレンダー(所有者=申請者Aのもの)が表示・編集される。「同じ日に別々の勤怠を持つ」といった競合の概念自体が生じない。

- **リゾルバ方式で実現する**: データの実体は従来どおりメールアドレス(`user_id`)をキーに分離保存したまま変えない。連携とは「認証済みメールアドレスを、有効なカレンダー所有者に変換する一段の写像(リゾルバ)」を1枚挟むことである。未連携なら自分自身に、連携メンバーなら所有者に解決し、勤怠記録・会社休日/営業日・設定・スケジュール・エクスポートのすべてがこの解決後のメールアドレスに対して行われる。マージ処理も同日競合の解決ロジックも不要。

- **完全に可逆(休眠データ)**: 連携メンバー(B)が連携前に貯めていたデータは、解決先が所有者に切り替わることで見えなくなるだけで削除しない。解除すればBは自分自身に解決されるようになり、休眠していた自分のカレンダーが元通り復活する。破壊的なデータ移行を一切行わないため、いつ連携・解除しても安全。

- **フラット・スター型に限定する**: 1つの所有者カレンダーに複数のメールが参加できる(3つ以上も可)が、「メンバーが更に別メンバーを持つ」連鎖と「1メールが複数カレンダーに同時参加」は禁止する。これによりリゾルバは常に一段で解決でき、可逆性と単純さを保つ。

- **申請→承認はアプリ内で完結**: このアプリにはメール送信基盤が無い(認証はCloudflare Accessのみ)。よって連携申請の通知・承認・却下・取消はすべてアプリ内(設定モーダルのセクション+ヘッダーのバッジ)で行い、外部通知に依存しない。認証自体は連携後も各メールアドレスごとにAccessで別々に行う(リゾルバはJWT検証後の`userId`にのみ作用するアプリ層の概念)。

## 検討した代替案

- **切り替え(スイッチ)方式**: 各メールのデータを分離したまま、管理者の閲覧ビューのように「自分/相手のカレンダー」を切り替えて見る案。ユーザーの求める「1つのカレンダー」像には最も遠く、UIも増えるため不採用。
- **マージ方式**: 連携時に一方のデータを他方へ取り込む案。同日競合の解決ルールと、解除時の再分離の設計が必要で非可逆寄りになるため不採用。

## 帰結

- 連携メンバーは連携中、自分自身の(休眠)カレンダーにアクセスできない。承認時にこの旨を警告する。
- 完全共有のため、連携メンバーが設定(目標出社率・締め日等)を変更すると所有者の設定が変わる。これはエイリアスの本来の意味として意図した挙動。
- 管理者機能(`/admin`)はリゾルバの外に置き、従来どおり生の`user_id`を明示指定して閲覧する(連携を無視)。
