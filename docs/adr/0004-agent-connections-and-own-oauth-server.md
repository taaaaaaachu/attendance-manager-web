# エージェント接続をMCPと自前のOAuth 2.1認可サーバーで提供し、Accessの外に出す入口を限定する

自律型AIエージェント(muse・dots など)にMCPで勤怠を操作させるにあたり、以下を決定した。

## 決定

- **エージェント接続は発行者のメールアドレス1つに結びつく。** 操作先のカレンダーは接続に持たせず、呼び出しのたびにアカウント連携のリゾルバで解決する(画面と同じ。ADR 0002)。連携メンバーが発行した接続は所有者のカレンダーを操作し、連携を解除すればその時点から自分のカレンダーを操作する。
  - 作り方は2通り。OAuth 2.1の同意画面で作るものと、設定画面で手動発行するBearerトークン。どちらも同じ一覧で管理し、同じように取り消す。
  - 出すのは日常の操作(勤怠の閲覧・記録・削除、期間と出社率、設定、会社の休日・出勤日、祝日の閲覧、スケジュールの一括適用)だけ。アカウント連携・管理者機能(管理者が発行しても)・全件リセット・祝日の再取得(全ユーザー共通のデータ)は出さない。エージェントが書いた記録に印は付けない。
- **入口は `/mcp` の1本。** 公式TypeScript SDK v2(`@modelcontextprotocol/server` の `createMcpHandler`)をステートレスで使う。トークンは `/mcp` 以外(`/api/*`)では受け付けない。
- **OAuth 2.1の認可サーバーは自前で実装し、状態はすべてD1に置く。** `@cloudflare/workers-oauth-provider` も比較したうえで採らなかった。
  - クライアント登録はCIMDとDCRの両方。どちらも公開クライアント(認証方式 none、PKCE S256のみ)。`redirect_uri` は完全一致、ループバックの http だけポート違いを許す。
  - アクセストークンは寿命1時間の不透明トークン。リフレッシュトークンは使うたびに入れ替え、古いものが再び使われたら接続ごと失効させる。トークン・認可コードはSHA-256のハッシュだけを保存する。
  - 90日使われない接続は失効する(手動発行のトークンもそれ以外の期限は無い)。認可コードは60秒・1回限り。使われないまま30日過ぎたDCRの登録は消す。期限切れの行はCron Triggerで毎日消す。
  - DCRは誰でも呼べるので、IPごとの回数制限(Rate Limitingバインディング)と、未使用の登録数の上限(1,000件)を設ける。
  - 同意画面では追加の本人確認を求めない(Accessのセッションと明示的なクリックで足りるとする)。
- **Cloudflare Accessとの境界。** アプリにはログインが無く、身元はAccessのJWTから取っている。エージェントのサーバーはAccessを通れないため、次のパスだけをAccessの**Bypass**にする(ダッシュボードの設定。手順はREADME)。
  - Bypass: `/mcp`、`/oauth/token`、`/oauth/register`、`/oauth/revoke`、`/.well-known/*`。これらのルートは `requireAccessAuth` を通さず、トークン・認可コード+PKCEだけで認証する。
  - Accessの内側に残す: 同意画面 `/oauth/authorize`。AccessのJWTの身元で「誰が許可したか」を決める。POSTは同じオリジンからの送信だけを受け付け(CSRF対策)、`X-Frame-Options: DENY` で埋め込みを禁じる。
  - `workers_dev`・`preview_urls` の無効化は維持する(Accessを迂回させないため)。
- **管理者は全員の接続を取り消せる。** `/mcp` はAccessを通らないので、Accessのポリシーから外した人の接続も動き続ける。アプリからは「今もAccessで許可されているか」を問い合わせられないため、管理画面に全接続の一覧と取り消しを置く(勤怠記録の無い人の接続も出す)。管理者のユーザー削除でも、その人の接続を消す。

## 検討した代替案

- **`@cloudflare/workers-oauth-provider`**: DCR・CIMD・SSRF対策・メタデータ・revokeが組み込みで、コードは最も少ない。しかし、ストアがKV必須(D1に揃えられない)で、リフレッシュトークンは直前の1本が新しい方の初回使用まで有効なまま(再利用検知で接続ごと失効、ができない)、OAuthの接続(KV)と手動発行(D1)の一覧が2か所に分かれる。これらを嫌って自前実装を選んだ。
- **Agents SDK の `McpAgent`**: Durable Objects前提のステートフルな作りで、勤怠の単発操作には過剰。
- **同意画面をSPA(React)で作る**: Service Workerと許可用APIの往復の考慮が増えるため、Workerが返すサーバー描画のHTMLにした。

## 帰結

- `agent_connections`・`oauth_clients`・`oauth_codes` テーブルを追加する(docs/db-schema.md)。
- Workersではisolateがリクエストをまたいで共有される保証が無いため、認可コードもD1に置く。CIMDの文書はキャッシュせず、同意画面の表示と許可のたびに取得する。
- CIMDの取得では送信先のIPを確かめられないので、`global_fetch_strictly_public`(互換性フラグ)・リダイレクト不追従・5秒/10KBの上限・IP直書きと既定外ポートの拒否で守る。
- 設定の変更とスケジュールの一括適用は、画面のAPIとMCPで同じ規則を使うようlibへ移した。
- DCRの回数制限の値はwrangler.jsoncとvitest.config.tsの両方にある(テスト用のpool-workersが `ratelimits` を読めないため)。
